# Tokenbench study library

The `study` package currently implements the preregistered, harness-neutral analysis boundary. It does not launch runs, invoke a particular model harness, publish evidence, or provide a CLI command. Those integrations remain separate work.

## Current contracts

- `TaskCatalog` / `DecodeTaskCatalog` implement byte-canonical `tokenbench.task-catalog/v1`. The catalog is a closed 144-task Cartesian product over the twelve locked corpus repositories, three task families, and four size tiers. Each task binds exact upstream/corpus provenance, Git and content identities, direct commands and timeouts, fixed tier ceilings, blinded quality items, hidden evaluator identity, preregistered exclusions, and a code-only gold-patch identity.
- `TaskBundle` / `DecodeTaskBundle` implement byte-canonical `tokenbench.task-bundle/v1`. The bundle commits the decoded catalog SHA-256 and its exact 144 sorted task IDs to 480 bounded, content-addressed prompt, pinned-toolchain, hidden-evaluator, and code-only gold-patch references. References are opaque CAS identities with fixed role media types; this layer does not open or execute them.
- `LoadAuthenticatedTaskBundle` accepts only a caller-supplied CAS copy capability, validates the complete catalog/bundle again, and streams each distinct reference through independent size and SHA-256 authentication. Its immutable typed handles reauthenticate one role-bounded object before returning fresh bytes, detect replacement after load, and never parse, unpack, execute, or accumulate the full artifact set.
- `Policy` / `DecodePolicy` implement byte-canonical `tokenbench.study-policy/v3`. Every task is exactly one of `code`, `review`, or `explain`. Review/explain tasks preregister exactly two distinct, sorted canonical evaluator IDs plus deterministic `arithmetic_mean` aggregation. Code tasks have no prose criteria or evaluator path.
- `InputManifest` / `LoadAuthenticatedCorpus` implement byte-canonical `tokenbench.study-inputs/v2`. Every included task/repetition is bound to an authenticated capture or replay root, or to one explicit preregistered not-attempted reason. Run identity, task, prompt, repetition, and common execution configuration are derived from verified evidence rather than caller-authored summaries.
- `BlindPair` accepts only the two final answers plus their preregistered review/explain task and repetition. It verifies the secret blinding seed, derives the label assignment and nonce deterministically, and emits `tokenbench.blind-evaluation/v3`. The packet contains no treatment, run order, repetition, pair ID, traces, token counters, failure metadata, or other evaluator's output. Code tasks are rejected at this boundary.
- `Evaluator` receives only a defensive copy of that packet. `VerifyEvaluations` requires exactly two outputs in preregistered evaluator-ID order, exact label/item order, and echoed nonce and packet commitment. `tokenbench.verified-quality/v3` preserves both complete individual outputs, their digests, and treatment-mapped item matrices, then computes the preregistered arithmetic mean. Missing, duplicate, reordered, or identity-substituted judgments fail closed.
- `ObjectiveCodeQuality` is a disjoint sealed boundary for later authenticated patch/test outcomes. There is deliberately no production constructor or code runner in this milestone. Consequently, code quality may currently be explicit-missing, but it cannot be fabricated by a prose evaluator.
- `BuildPairRecords` derives the complete ordered analysis matrix only from an authenticated corpus. Verified quality packets must commit the exact authenticated answers; exclusions, failures, counters, missing answers, and not-attempted slots cannot be supplied or overridden by report callers.
- `Analyze` requires exactly one ordered `PairRecord` for every included task/repetition. A missing attempt, failed arm, missing answer, unavailable judgment, or permitted post-attempt exclusion remains an explicit record with a reason. Omitted, duplicate, reordered, or extra records fail closed.
- `tokenbench.study-analysis/v3` starts with attempted/failure/exclusion/completeness counts and separates judged from objective-code quality. Its inter-rater section identifies the two preregistered evaluators and discloses exact agreement/disagreement at pair and answer/item level plus normalized absolute score-difference distribution. It then reports input, cached input, cache-write input, output, reasoning, primary input-plus-output, and optional provider-native totals independently. Provider totals include only both-present pairs and disclose missingness; they never replace the primary metric.

## Statistical rules

Pair-level component reports include baseline/candidate distributions, candidate-minus-baseline deltas, ratio distributions, ratio of sums, mean, median, quartiles, and extrema. A positive value divided by a zero baseline and a zero/zero pair are counted separately; neither is assigned an invented finite paired ratio. A zero aggregate baseline makes the ratio of sums undefined.

Inference first averages repetitions within each task and then tasks within each preregistered repository cluster. Up to the preregistered small-sample limit, the two-sided repository-cluster sign-flip p-value enumerates every assignment. Above it, a deterministic SHA-256 counter stream drives the preregistered Monte Carlo sample count and the report uses the conservative plus-one p-value. The repository-cluster percentile bootstrap uses a separately committed seed and preregistered confidence/sample settings for primary-token and quality mean-difference intervals.

A `demonstrated` token-efficiency decision requires every preregistered gate: minimum complete pairs and tasks, maximum failures/exclusions/not-attempted/missing answers, enough verified quality pairs/tasks, candidate answer-threshold pass rate, quality noninferiority confidence bound, a nonzero baseline total, minimum token reduction, and the randomization p-value threshold. Otherwise the result is `not_demonstrated` only when all eligibility/quality gates passed, or `inconclusive` when they did not. Policies cannot authorize a one-pair or one-task claim.

The JSON schemas in `schemas/` document the current versioned wire objects, including the task catalog, task bundle, verified judged quality, and reserved objective-code boundary. Go validation is stricter where JSON Schema cannot express sorted uniqueness, family-dependent contracts, locked repository mappings, cross-document artifact commitments, cross-field totals, packet-to-policy equality, committed-seed verification, authenticated evidence lineage, evaluator label/item correspondence, or private capability seals.
